Build timeline on the 2 GB host
Before
After

Before: 6 PHP extension compiles, 3 npm ci and 2 vite builds compete for 2 GB. After: crm → payment → dashboard, one at a time.

Problem
podman-compose build starts one task per build: block, all in parallel (podman_compose.py:2981). That means 11 simultaneous builds and 11 tags.
Solution
Give each Dockerfile one image: name with ${IMAGE_TAG:-latest}. Keep build: only on crm-migrate, payment-api-1 and dashboard-1; the other 8 services get image: only.
Wins
  • Build count drops 11 → 3
  • No parallel OOM storm
  • 8 duplicate tags deleted
  • One image to roll back
02

Bounded container logs

Strong compose
  • docker-compose.yml
Before · no logging: anywhere
After · max-size: 10m per container
x-logging: &logging
  driver: json-file        # podman aliases json-file → k8s-file
  options: {max-size: "10m"}

x-app-defaults: &app-defaults
  logging: *logging        # plus explicit lines on crm-migrate, postgres, redis, rabbitmq, gateway
Problem
Log files grow without limit. On the podman journald default they are capped only by journald's global limit, which can be up to 4 GB.
Solution
A shared x-logging anchor with only max-size, the one option both Docker and Podman accept.
Wins
  • About 170 MB worst case
  • Same config on Docker and Podman

Skipped on purpose: cpus. Rootless podman often lacks a delegated cpu cgroup controller, and containers would fail to start. Swap stays available; both runtimes default swap to 2× mem_limit.
Problem
No container has a memory ceiling, so a Horizon spike can starve postgres and redis.
Solution
Add one mem_limit line per service, sized from the limits each app already sets.
Wins
  • Runaway kills itself, not postgres
  • podman stats shows the budget

The 0.6 watermark is a ratio of host RAM. Under a 384m cap it is never reached, so the kernel kills the broker first. Also harmless in dev.

export IMAGE_TAG="$(git rev-parse --short HEAD)"
P="podman-compose --env-file .env.docker -f docker-compose.podman.yml"
$P build crm-migrate && $P build payment-api-1 && $P build dashboard-1
$P up -d
# after health + smoke checks pass: drop previous release tags, keep build cache
podman images --format '{{.Repository}}:{{.Tag}}' \
  | grep -E '^localhost/crm-(server|payment|dashboard):' \
  | grep -v ":$IMAGE_TAG\$" | xargs -r podman rmi
# monthly, or when `podman system df` grows (next build is a full rebuild)
podman image prune -f
With IMAGE_TAG unset (latest), up -d needs --force-recreate after a rebuild. podman-compose compares config hashes, not image digests.

Verification

  1. docker compose -f docker-compose.yml config -q and npm run quality:docker (same as CI).
  2. podman-compose --dry-run -f docker-compose.podman.yml build shows exactly 3 podman build commands.
  3. podman-compose -f docker-compose.podman.yml config | grep -E 'image:|mem_limit' shows the shared image names and the caps.
  4. The dashboard image contains /usr/share/nginx/html/docs/db/crm. After editing a dashboard source file, the erd stage is a cache hit.
  5. Local up -d: podman stats --no-stream shows a MEM LIMIT for each container, gateway LogConfig shows max-size 10m, curl -fsS 127.0.0.1:8080/healthz succeeds, and Horizon runs at most 2 processes.
  6. Prod pre-check if rootless: user@$(id -u).service/cgroup.controllers lists memory.
Warning, not in this plan: deploy.sh runs art migrate:fresh --seed on the server. That wipes the CRM database on every deploy.
RabbitMQ definitions: entrypoint.sh generates /tmp/definitions.json (bootstrap user + topology.json) on a tmpfs at boot, and rabbitmq.conf loads it. The management plugin is unused in prod; the plain -alpine image would need core load_definitions instead of management.load_definitions.
Top recommendation

01 · One build per image

On a 2 GB host, 11 concurrent builds is the main source of swap thrash and OOM risk. Removing 8 build: blocks fixes it.
